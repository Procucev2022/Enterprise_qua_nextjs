# D1 binding and cache-miss fixes for test-v3 environment

Two targeted configuration and code fixes applied to resolve failing Cloudflare Worker APIs in the test-v3 environment. The fixes address a D1 database binding initialization failure causing atomic transaction rejections (503 PERSISTENCE_UNAVAILABLE) and a cache-miss pattern causing RFQ lookups to fail on cold Worker starts (500 Internal Server Error).

**Watch for:** Database binding inconsistency across environments (confirmed: stage has account_id, production environments lack it in visible config); no test coverage exists for the cache-miss scenario that caused the 500 error; the account_id value is shared across test and stage environments.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The D1 binding fix adds the missing `account_id` to the test environment configuration in wrangler.jsonc. Without it, `getD1Binding()` returns null or an invalid binding, causing the quote submission path to fall back to the D1 HTTP REST API client, which explicitly rejects atomic transactions with a 503 error. The fix aligns the test environment with the stage environment's configuration, using the same account_id value.

The email-preview endpoint was using the synchronous `getRFQById()` method, which only reads from the in-memory `rfqs` array. On Worker cold starts or when the cache is empty, this returns null even when the RFQ exists in the database. The fix switches to `getRFQByIdAsync()`, which falls back to a database query when the cache misses, matching the pattern already used by other RFQ endpoints like `downloadRFQ` and `addQuote`.

The production and prod environments in wrangler.jsonc are not visible in the reviewed sections, so their account_id configuration status is unknown. If they also lack account_id, they would exhibit the same D1 binding failure on atomic transactions.

The existing test suite extensively covers both endpoints, including the quote submission flow with persistence and the email-preview endpoint's access control and RFQ resolution. However, no test explicitly exercises the cache-miss scenario that the async lookup fixes — all tests run with a warm cache where `getRFQById()` succeeds.

## D1 binding initialization via account_id

The test environment configuration in wrangler.jsonc was missing the `account_id` field that the stage environment declares on line 67. Without account_id, the Cloudflare Workers runtime cannot initialize the D1 database binding referenced by `globalThis.__CF_ENV__.DB`, causing `getD1Binding()` in d1Bridge.js to return null.

When the D1 binding is unavailable, `pool.hasStorage()` still returns true because `getD1HttpClient()` succeeds — it's configured with `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_D1_DATABASE_ID` environment variables for Node.js development. This creates a mismatch: the application believes storage is available, but the atomic transaction path in `vendorQuoteSubmissionQueries.js` (line 637) explicitly rejects the D1 HTTP client because it cannot handle multi-statement transactions. The result is a 503 PERSISTENCE_UNAVAILABLE error.

The fix adds `"account_id": "0f0b77c43d76a2c5c5282e7e0f80b607"` to line 232, immediately after the test environment's `name` field. The database_id differs (test points to `3e7bf79b-c24d-406d-9d66-b42d56e4c5ad`, stage points to a different ID) — separate D1 databases for separate environments.

## Cache-miss handling in email-preview

The `generateEmailPreview` endpoint (rfqController.js line 2320) was calling `storeService.getRFQById(id)` synchronously. This function reads only from the in-memory `rfqs` array (storeService.js line 4706). On a Worker cold start or when the cache hasn't been populated yet, the array is empty even though the RFQ exists in the database. The endpoint's access check passes null to `canAccessRfq`, which returns false, triggering a 404 response. If the RFQ is somehow in the array but incomplete, `generateStandardRFQEmail()` throws when it checks `!rfq.rfqNumber`, which propagates through the catch block and becomes a 500 error.

The fix changes line 2324 from:

```javascript
const rfq = storeService.getRFQById(id);
```

to:

```javascript
const rfq = await storeService.getRFQByIdAsync(id);
```

The async version (storeService.js line 4674) queries the database via `domainQueries.getRFQByIdFromDB(id)`, hydrates the in-memory cache, and returns the normalized object. If the database query fails, it throws PERSISTENCE_UNAVAILABLE (503) rather than silently returning null — a database failure surfaces explicitly instead of masquerading as "RFQ not found."

This matches the pattern used by `downloadRFQ` (line 2283), `addQuote` (line 2154), and `updateRFQ` (line 1877).

## Consistency across RFQ lookup call sites

A grep of rfqController.js shows 23 call sites for `getRFQById` or `getRFQByIdAsync`. Most use the async version. The synchronous `getRFQById()` appears in three remaining places:

1. **Line 2091** (`deleteRFQ`): Delete operations typically happen within the same isolate session that created the RFQ, so the cache is warm. If a buyer deletes from a different isolate, they get a 404 — acceptable degradation, not a crash.

2. **Line 1877** (`updateRFQ`): Uses `getRFQById(id) || (await getRFQByIdAsync(id))` — tries cache first, falls back to database. Updates often happen in the same session as creation, so the cache-first check avoids a database roundtrip in the common case.

3. **Controller export line 2608**: The exported function name `getRFQById`; it's the route handler, not the store service call.

The pattern is consistent: endpoints that might execute on a cold isolate (quote submission, downloads, email preview) use the async version; endpoints that are session-local or have an explicit cache-first strategy use the synchronous version or a guarded fallback.

## Error handling paths

**Quote submission**: If `getRFQByIdAsync()` throws (database unavailable), the error propagates to the catch block at line 2237, which logs it and calls `next(err)`. The Express error handler converts it to 503. If the RFQ is not found, `canAccessRfq` returns false and the endpoint returns 404 with "RFQ not found or out of scope."

**Email preview**: If `getRFQByIdAsync()` throws, the catch block at line 2342 logs the error and calls `next(err)`, resulting in 500. If the RFQ is not found, the access check fails and returns 404.

The async lookup's explicit PERSISTENCE_UNAVAILABLE error on database failure distinguishes "RFQ does not exist" from "database is down," better than the synchronous version's silent null return.
