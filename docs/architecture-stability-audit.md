# Architecture and data stability audit

Audit date: 2026-11-05

## Scope and evidence

This is a repository and local-D1 audit. It compares the PostgreSQL and D1 schema files, traces the shared query adapter, checks indexes and fallback behavior, and applies the current D1 schema to the local Wrangler database. It does not claim to have inspected production rows or production D1 analytics. An earlier diagnostic invocation ran the remote migration script; all 139 DDL attempts returned HTTP 404 for the configured database ID. The new read-only aggregate audit also returned HTTP 404 for that ID, so no production reads or writes were accepted. On 2026-11-05, `wrangler d1 list --json` returned an empty list under the current Wrangler identity, so the intended production database is not available through the configured account context. Live row counts, duplicate scans, and quota utilization remain unverified.

## Changes made

- `pool.query()` now honors the documented `{ d1: true }` opt-in. Before this, the presence of any D1 binding routed every query—including PostgreSQL-only features—to D1. The query now emits a structured error log with a SQL fingerprint, table, backend, duration, and parameter count, without logging parameter values.
- The PostgreSQL schema now has `chaser_queue`; the D1 schema now has `document_vault`. The two schemas previously each had 38 tables but differed by these two tables.
- Removed redundant explicit indexes for `vendors.email`, `rfqs.rfq_number`, and `buyer_accounts.corporate_email`. Each column already has a UNIQUE constraint and therefore an index. Fresh schemas no longer create the duplicate index writes/storage. Existing deployed duplicate indexes need a deliberate cleanup migration after confirming use.
- The D1 migration script now records every failed statement and exits unsuccessfully after it finishes collecting results. It previously counted failed SQL as skipped and printed a successful completion message.
- Added an idempotent local-only fixture and `npm run db:seed:mock:local`. It seeds one buyer, vendor, and RFQ in Wrangler's local D1 database; it never passes `--remote`.
- Cleaned the frontend hook dependency and font-placement warnings. Long-lived loaders now use a latest-value ref so adding hook dependencies does not restart hydration or cause duplicate fetches; the redundant layout-level font links were removed while the existing global stylesheet font import remains.
- Ported document-vault list/get/create/update/delete queries through the explicit D1 route and replaced PostgreSQL-only `ILIKE` with portable case-insensitive `LIKE`. Configured database failures now fail closed instead of returning sample records or reporting a memory-only create/update/delete as durable; the controller returns a retryable 503.
- Routed payment-dues acknowledgement updates through D1 and added SQLite `json_extract` matching for gateway message IDs. Account, vendor, communication, acknowledgement, and history reads/writes now fail closed when configured persistence errors occur; writes no longer report memory-only communication or acknowledgement changes as saved. The API returns a retryable 503 for these failures.
- Reduced payment-dues list hydration from the full communications history to latest rows for eligible low-credit account IDs, selecting only status fields. Local D1's query plan uses the existing account/time index. Configured read failures are logged with structured errors and no longer substitute stale store or isolate-local records.
- Fixed internal-task credit balance reads to opt into D1; they previously swallowed the adapter's "database not configured" failure and omitted the current balance on Workers.
- Ported internal-task credit approval to one atomic D1 Worker batch, aligned buyer/vendor balance aliases, and kept PostgreSQL account, ledger, activity, and task writes on one transaction client. Added structured logs for D1 batch outcomes and nonblocking balance-read failures.
- Added `payment_dues_communications` to both schemas after finding it was referenced by payment-dues queries and migration row-count reporting but declared in neither schema. Added account/time indexes and a schema regression assertion so this durable workflow no longer depends on process memory after migration.
- Replaced process-only management approvals with numbered PostgreSQL and D1 migrations for durable approval rows and append-only decision events. Approval decisions now update state and write the audit event in one PostgreSQL transaction or one atomic D1 Worker batch; repeat decisions return 409, and configured storage failures return retryable 503 responses. The previous approval audit insert targeted columns that did not exist in either schema and silently discarded failures.
- Removed the stale in-memory buyer-account fallback after a configured database lookup error. The service now logs the full error and propagates a retryable persistence error so account identity and authorization decisions do not use out-of-date cached values.
- Replaced process-only client registration decisions with PostgreSQL transaction and D1 Worker-batch writes. The migration adds durable registration events with actor, action, prior/new status, and remarks; repeat decisions return 409, and configured storage errors return retryable 503 responses. Database listings now filter buyer roles in SQL, paginate and count in the database, and never merge demo rows or stale memory into configured storage results.
- Protected every `/api/internal-tasks` route with authentication and admin/category-manager role checks. The registrations dashboard now sends its bearer token; task exports remain available from the already-loaded client data without navigating to an unauthenticated export URL.
- Added centralized registration filter validation and structured failure logs. Registration search logs record only whether a query exists and its length, not an email address or phone number.
- Added a composite `(role_uuid, created_ts DESC, uuid DESC)` index for buyer registration pagination. A local D1 `EXPLAIN QUERY PLAN` confirmed `SEARCH user USING COVERING INDEX idx_user_role_created`; the insert-only decision event and state update were smoke-tested against local D1 and the temporary event was removed.

## Database findings

### Confirmed from schema and query code

- Organization category uniqueness is now enforced for active rows by numbered migrations. The migration deactivates blank rows and duplicate normalized pairs without deleting their history; production application remains unverified because the configured D1 database ID returned 404.
- `payment_dues_communications` was missing from both schema files even though its repository and migration report referenced it. Failures were swallowed into memory, so communication history and acknowledgement updates could disappear on restart. The table is now declared in both schemas; production deployment still needs the corrected schema applied.
- `vendor_catalogue` still has no schema-level SKU uniqueness index, so legacy rows or direct SQL writers can bypass the application write guard; any unique-index migration still needs production duplicate reconciliation. Evaluation lifecycle uniqueness also remains undefined and must follow product semantics.
- Unique email fields are case-sensitive in SQLite unless normalized by the application. Existing `vendors.email` and `buyer_accounts.corporate_email` data can therefore represent the same address with different casing. Normalize before adding a case-insensitive uniqueness constraint.
- Vendor email writes now normalize casing and whitespace, and profile category replacement is serialized. Legacy vendor-email case variants still need a read-only production duplicate count before a safe vendor uniqueness migration can be designed.
- The old D1 migration path sent 139 statements individually. This is a high request count for schema setup and can consume D1 API operations; use Wrangler local migrations for development and batch/controlled deployment for remote schema work.
- D1 and PostgreSQL migration commands now skip full schema replay after checksum baselines and skip row-count scans unless requested. PostgreSQL uses a session advisory lock and transactional numbered migrations; D1 uses an owner-scoped five-minute renewable lease around the REST migration sequence. D1's initial schema/backfill remains a one-time remote operation.
- The in-process query cache is not shared across Worker isolates. Its read savings and invalidation behavior cannot be treated as global D1 utilization reduction. Worker cold-start hydration is bounded and skipped for health/database-only paths, but `storeService` still launches many domain writes in the background; `waitUntil` keeps them alive, while the caller can still return success before persistence failure is known.
- Payment-dues latest-status hydration now requests only low-credit account IDs, returns one row per account with only display fields, and uses `ROW_NUMBER()` with the existing `(account_id, sent_at DESC)` index. A local D1 `EXPLAIN QUERY PLAN` confirms indexed `SEARCH` by account ID. It still reads matching communication rows for each eligible account; production D1 row-read metrics are needed to quantify the reduction.
- D1 and PostgreSQL schemas are manually maintained equivalents rather than one generated source. The missing-table pair demonstrates the drift risk.
